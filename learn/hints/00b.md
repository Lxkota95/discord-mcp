# Checkpoint answers — milestone 0b

Try the questions in `00b-design.md` first. These answers are short; the reasons are in `design.md`.

## The error classification task

| Situation | Kind | Why |
|---|---|---|
| Line isn't valid JSON | Protocol (-32700) | Nothing a model can fix: a client or transport bug |
| `tools/call` for a non-existent tool | Protocol (-32602, "unknown tool") | The request itself is wrong |
| Discord answers 403 | Tool execution (`isError: true`) | The model can explain it, or try something it *is* allowed to do |
| Role name of 200 characters | Tool execution (`isError: true`) | The model can shorten it and retry |
| Protocol version `1900-01-01` | Protocol (-32022) | A version mismatch for the client to resolve |

## The safety task

Several guardrails apply: no message-reading tools (much less untrusted text reaches the model), the
permission prompt (you'd see an unexpected "give everyone admin" call before it runs), least
privilege (the bot can't grant Administrator if it doesn't have that permission), the guild
allowlist, and preview-then-confirm. Most people pick **least privilege**: it holds even when every
other layer fails.

## Checkpoint questions

1. Claude Code starts the server as its own child process, so stdin/stdout is the simplest private
   channel: no ports, no network exposure, no authentication to set up, and the server lives and dies
   with the client.
2. Anything that isn't a valid MCP message: no `println!` debugging, no banners. Logs go to stderr.
3. A request has an `id` and must get exactly one response with that `id`; a notification has no
   `id` and must never get a reply, not even an error.
4. By design (architecture principle 3): the host keeps the conversation and only forwards tool calls.
   Each server gets only what it needs, so a compromised or buggy server can't read your chat.
5. Every request carries its own protocol version (and client capabilities) in `params._meta`, so
   the server needs no memory of earlier requests. `server/discover` replaced `initialize` for
   learning what a server supports.
6. The *protocol* exchange worked fine; the *tool* failed. Reporting it as a tool result gives the
   model a readable message it can act on (self-correct and retry), which a JSON-RPC error mostly
   wouldn't.
7. Milestones 1–5 need nothing from Discord, and 6–9 use recorded responses. The layering keeps
   protocol code separate from the Discord client, so each can be tested in isolation; only
   milestone 10 touches the real Discord.
